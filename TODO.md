- **No undo for a mis-marked `Delivered` shipment** (surfaced by the bianka reviews design critique, C16, 2026-08-25). `Shipping/Enums/ShipmentStatus::allowedTransitions()` returns `[]` for `Delivered`, `UpdateShipmentStatus` enforces `canTransitionTo`, and `ShipmentsRelationManager` hides every action on the same check — so a fat-fingered "Entregado" on a parcel still in the post is permanent through every sanctioned surface. Flagged, not scheduled.

- **A failed refund is never undone** (R4 of the dashboard-refund brief, § 5.4; flagged 2026-10-05, not built). A refund is recorded while Stripe reports it `pending` or `succeeded`. If it later fails, the `Refund` row, its VAT reversal and `payments.amount_refunded` all stay as they were. That holds for admin refunds and, since v0.71.3, for refunds made outside the app. It gets worse *if* Stripe lowers the charge's `amount_refunded` when a refund fails: the next real refund's cumulative can then sit at or below the stored total and be dropped as stale, so it is never recorded. Whether Stripe does that is stated nowhere we read. **First step: one test-mode run with Stripe's failing-refund test card** (docs.stripe.com/testing, under refunds: the card whose refund fails asynchronously). Save the bodies it sends into `tests/Fixtures/Stripe/` and note whether a `charge.refunded` or `charge.updated` with a lower cumulative follows; that settles the shape. For whoever builds it: `ProcessPaymentWebhook::applyRefund()`'s `max()` and the unlocked-read shortcut in `gatewayRefundsFor()` both assume the total never falls, so both have to be revisited; and the driver ignores `charge.refund.updated` and `refund.failed` today, so one of them has to be handled.

- **A dispute leaves no local record and raises no alert** (dashboard-refund brief § 5.5; flagged 2026-10-05, not built). A dispute is not a refund: the bank withdraws the money, there is a fee, and it can be won back. Since v0.71.3 the Stripe driver ignores `charge.dispute.*` with one `Log::info` naming the event; before, it cast the event to a payment intent and dropped it without a trace. Both consumers run `LOG_LEVEL=warning`, so that line lands nowhere in production: Stripe's own e-mail and dashboard are the only signal, and the order page keeps offering a refund of money the bank has already taken. Decision needed on the shape before building. At least: an event the consumers' operator alert picks up. At most: a local dispute record, shown on the order page and counted against the refund cap. Check first which `charge.dispute.*` events each endpoint has enabled.

- **`RecordRefund`'s VAT anchor assumes one refunded payment per order** (found reviewing the dashboard-refund build, 2026-10-05; flagged, not built). The anchor is `max(order's refund rows + this refund, this payment's amount_refunded)`: the first figure is order-wide, the second belongs to one payment. An order with two succeeded payments (a duplicate charge) and refunds on both can reverse more VAT than was charged: 1760 refunded in full on one payment, then 500 on the other, reverses 269c of 210c, because `ReverseTax` does not clamp its cumulative at the order total. Neither consumer creates a second succeeded payment today, and the code before v0.71.3 was wrong for this shape as well (negative lines). Cheapest fix if it is ever needed: clamp the cumulative at `order.total` in `RecordRefund`.

## Deferred / Watch

- ⚠️ **`Media::fileIsShared()` has a benign concurrent-delete race — flagged 2026-09-01, deliberately not fixed.** The guard is a read (`exists()`) followed by a delete, with no lock between them, so two simultaneous deletes of rows sharing one `disk`+`path` can each see the other still present and each skip the disk delete — leaving a **leaked file** with no rows pointing at it. It can never lose a file a live row still needs, which is the failure the guard exists to prevent; the residue is wasted bytes. Sequential deletes — the only path an admin actually produces — resolve correctly, the last row taking the file with it. Not fortified because the cost is disk space, the trigger needs two concurrent deletes of path-sharing rows, and the alternatives (a lock, or a sweeper) both buy more machinery than the problem. **Revisit if** shared paths stop being an artifact of the save-churn replacement case and become a normal state (e.g. deliberate media deduplication), at which point a periodic orphan-file sweep is the shape — not a lock.

- 💭 **Convert `InitiatePayment` to a published FlowChain** — `InitiatePayment`'s 5 internal steps (gateway resolve → payment record create → customer ID resolve → session create → gateway-reference write-back) would let consumers insert fraud check pre-session, analytics ping post-session, custom customer-resolution branch, etc. without forking the action. **Blocked on sub-chain machinery** (`->chain()` builder method + `FlowChainBridge` interface, child step results nest into parent's `FlowChainResult`) — see FlowChain README §Child Chains for Option B/C design. AddToCartChain (v0.22.0) is the first published chain and proves the basic `PublishableFlowChain` path works; InitiatePayment specifically needs the nested-chain primitive that's still unbuilt. Narrower than "convert all of Payment": `RefundPayment` shouldn't be split (lockForUpdate + intentional gateway-call-before-DB-write ordering doesn't fragment cleanly), `ProcessPaymentWebhook` doesn't fit either (early-return-null successful no-ops, no parent chain to nest into). Trigger to un-defer: a real consumer extension request, OR new payment surface area (subscription renewals, 3DS retry, manual charges) that adds steps the current single action can't cleanly accommodate.

- 💭 **`AttachTag` / `AttachCategory` are not idempotent — and the premise here was wrong** (re-checked 2026-08-25). The note used to say a second attach "creates a duplicate pivot row". It cannot: `taggables` and `categorizables` both carry a UNIQUE index (since the 2026-04-08 extraction), so the second attach **throws a raw `QueryException`** — a 500 for any caller that doesn't pre-check. **There is also a later, opposite ruling on file:** `AttachDetachCategoryTest` (2026-05-29, `93b7db9`) pins the throw as the contract and says "if the consumer wants idempotency they must wrap with `syncWithoutDetaching` or similar at the call site". So this needs Jelte's pick, not a build slot — **it was implemented and reverted 2026-08-25** for exactly that reason.
  - Evidence for moving idempotency into the action: the call-site policy has already produced one hand-rolled bypass and one unguarded call. `in-other-worlds`' `AttachTagToContent` agent tool pre-checks `$content->tags->contains(...)` and then calls `$content->tags()->attach()` **directly, skipping the action** — so an agent-attached tag dispatches **no `TagAttached`** and never reaches the audit log. `CreateContentTranslation` calls `AttachCategory` with no pre-check at all, so translating a sibling into a category it already has 500s.
  - Fix shape if the ruling flips: `syncWithoutDetaching([$tag->getKey()])` in both actions, dispatch the event only when `$changes['attached'] !== []` (load-bearing for `AttachCategory` — `MaintainCategoryCounts` would otherwise re-increment every ancestor for a membership that already existed). The two `*_violates_the_unique_pivot_constraint` tests get retargeted onto a direct-`attach()` call so the DB net stays pinned.
