## Deferred / Watch

- 💭 **Convert `InitiatePayment` to a published FlowChain (`->chain()` locked in)** — the actual driver is publish-and-modify (FlowChain's primary purpose): a chain-shaped `InitiatePayment` lets consuming projects insert steps — fraud check pre-session, analytics ping post-session, custom customer-resolution branch, etc. — without forking the action. `->chain(class-string<FlowChainBridge>)` is the locked-in mechanism (no Option B intermediate). Narrower than "convert all of Payment": `RefundPayment` shouldn't be split because its `lockForUpdate` + intentional gateway-call-before-DB-write ordering doesn't fragment cleanly across FlowSteps; `ProcessPaymentWebhook` doesn't fit either (early-return-null branches are *successful* idempotent no-ops, which FlowChain has no primitive for, and it has no parent chain to nest into anyway). Conversion target is `InitiatePayment`'s 5 internal steps: gateway resolve → payment record create → customer ID resolve → session create → gateway-reference write-back. Trigger to un-defer: a real consumer extension request, OR new payment surface area (subscription renewals, 3DS retry, manual charges) that adds steps the current single action can't cleanly accommodate. Scope when picked up: `->chain()` builder method + `FlowChainBridge` interface, child step results nest into the parent's `FlowChainResult`, restructure `InitiatePayment` as a FlowChain with bridge wrapper. Consumer adoption: `ProcessCheckout`'s final step becomes `->chain(InitiatePaymentBridge::class)`.
- 💭 **Publish-and-extend mechanism for FlowChains (foundational)** — FlowChain's stated primary purpose is publishable chains that consumers modify (insert alert/email/analytics steps without forking). No chain in either repo currently exposes this — `ProcessCheckout` builds its chain inline with hardcoded `->step(...)` calls; the package ships zero published chains. Decided shape (2026-05-10): `vendor:publish`-style. The package ships its default chain definition as a file; the consumer publishes a copy into their app (e.g. `app/Flows/CheckoutFlow.php`); the framework discovers the consumer's copy first and falls back to the package's copy if absent. Once published, the consumer owns the file and edits it directly — adding steps, removing steps, swapping imports — using the existing builder API (`->step(...)`, `->when(...)`). No `insertBefore` / `insertAfter` / `replaceStep` extension API: redeclaring the chain is the modification mechanism, which keeps the resulting structure visible in one place and avoids anchor-by-class-name coupling. Open call: convention-based path discovery (`app/Flows/{Chain}Flow.php` auto-discovered) vs. config registration (`config/commerce.php` → `flows.checkout` → class-string), or both — decide when the first override actually lands. Upgrade story: when the package adds a new step to its default chain, consumers who've already published need to manually merge — same as Laravel's `vendor:publish` for views/configs. Mitigated by an upgrade-notes section in the package CHANGELOG when defaults change. **Step-discipline preconditions** that must be solved alongside the publish mechanism (or before each chain becomes publishable): (1) **granularity** — one step = one verb; existing offenders include `SelectShippingMethod` (zone resolve + method pick + cost calc) and `CreateCheckoutOrder` (persist + build shipping snapshot + build tax snapshot), both need splitting; (2) **stable payload contracts** — once a step's read/write surface is published, field names and types are public API and only grow by addition; (3) **no hidden conditional sub-behaviors** — branching belongs in the chain via `->when()`, not buried inside steps; (4) **explicit `@reads` / `@writes` docblocks per step** instead of runtime assertions encoding ordering coupling; (5) **naming conventions** — verb-noun step names with precise scope (`ResolveTaxRateForOrder` ✓, `HandleTax` ✗), domain-first payload field names with no abbreviation drift (`taxRate` everywhere, never alongside `tax_rate`). These conventions live in a "How to write a publishable FlowChain step" addition to the FlowChain README; existing steps get audited against them when each chain becomes a publish-target. Trigger to build: first real consumer extension request — until then no design pressure to nail down the discovery path.
