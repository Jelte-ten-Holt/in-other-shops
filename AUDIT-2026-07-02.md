# in-other-shops — Package Audit (2026-07-02)

Multi-agent audit across four lenses: **security**, **design/maintenance scale**, and **DRY/simplification** (split into domain-logic and scaffolding sweeps). Runtime-data scale is deliberately low (small catalog by design; the escape hatch for real scale is a search tool, not query rewrites), so N+1s and missing indexes are out of scope unless egregious. Known correctness pathologies (checkout/payment/tax/inventory/refund) are tracked in the `silent-correctness-audit*.md` files at projects-root and are **not** re-reported here.

Prior audits built on: `docs/audits/2026-04-24/security-audit.md`, `docs/audits/2026-05-13/dep-graph-audit.md`.

Status: **complete** — five passes (Security, Design-scale, Scaffolding DRY, Agent-domain DRY, domain-wide DRY). Section 4 (Agent domain) is a subset of Section 5's Agent findings — items AG-H1/M1/M2 there are the same as Section 5's M1/M2; read Section 5 for the full domain-logic sweep.

---

## Top priorities (cross-cutting synthesis)

Two findings surfaced independently from **both** the security and design agents — treat these as the headline:

1. **Filament resources ship with zero authorization and are hardcoded to package models.** Security frames it as default-allow (SEC M-A); design frames it as the weakest extension point (DES H2). Same root: the admin layer is entirely consumer-side copy-paste with a fail-open default. A single missing policy mapping exposes order PII / customer records / supplier cost data to any panel user. **This is the highest-value fix** — ship a default-deny policy base + a Filament Plugin from the package.

2. **Agent admin elevation rests on a scope string alone** (SEC H-A) — if a consumer ever registers `agent.admin` as a grantable Passport scope, the open DCR + consent flow can mint an admin token to any logged-in customer.

Everything else is lower-severity or maintenance-scale.

# 1. Security

Scope: `src/` MCP/Agent surface, HTTP controllers/routes/requests, Filament policy coverage, raw SQL / deserialization / Media / SSRF, secrets/logging. Prior-audit items confirmed **shipped** (calibration): agent-tool scoping, morph-gadget rejection, `/mcp` throttle, `client_name` sanitization, DCR hardening, `require_resource`.

## HIGH

### SEC H-A. Admin elevation gated on scope string alone — no client-trust check
**Severity: HIGH · Confidence: Med**

`src/Agent/Http/Middleware/AuthenticateAgent.php:112-117` grants `is_admin` whenever the token carries the `agent.admin` scope (literal match). Nothing checks the token's *client* is confidential / first-party. DCR restricts the *registered* scope (`DynamicClientRegistrationController.php:142-148`), but Passport does **not** restrict which scopes a client may *request* at `/oauth/authorize`. For the documented "provision admin clients directly" path to work, the consumer must register `agent.admin` as a Passport scope — once defined, a public DCR-registered connector can request `scope=agent agent.admin`, and any logged-in customer walked through consent mints an admin token. That unlocks `AdjustStock`, unscoped `ListOrders`, `GetRecentProblems`.

- **Attack path:** DCR open by default (`AGENT_DCR_ENABLED=true`) → register public client → drive auth-code flow against any logged-in shop user requesting `agent.admin` → generic consent screen → admin token.
- **Mitigating:** metadata doc advertises only the base scope (`AuthorizationServerMetadataController.php:30`); requires consumer to have defined `agent.admin` as grantable. Hence Med confidence.
- **Fix:** in `AuthenticateAgent`, additionally require the client be confidential + on a first-party allowlist (`agent.auth.oauth.admin_client_ids`) or `client->firstParty()`. At minimum, document loudly that `agent.admin` must never be interactively grantable, and ship a provisioning command so consumers don't reach for `tokensCan`.

## MEDIUM

### SEC M-A. Package Filament Resources ship zero authorization — fully open unless the consumer wires a policy per model
**Severity: MED · Confidence: High**

Every shipped Resource (`OrderResource`, `CustomerResource`, `CustomerGroupResource`, `VoucherResource`, `TaxRateResource`, `CategoryResource`, `TagResource`, `PurchaseOrderResource`, `SupplierResource`, `Variants/OptionResource`) defines no `canViewAny`/`canAccess`/policy and no nav gating. Confirmed against pinned Filament v5.5.1 (`vendor/filament/filament/src/helpers.php:60-80`): no policy + no strict-authorization mode → `get_authorization_response` falls through to **allow**. The entire gate is the consumer registering `Gate::policy(...)` for every package model.

`in-other-worlds` wires all of them (`app/Providers/AppServiceProvider.php:107-125`) so it's covered today — but this is a per-consumer, per-model footgun that directly undercuts the multi-admin `can_manage_*` model. A single missing mapping (new package Resource, a second consumer like bianka, a config-swapped model) exposes order PII / customer records / supplier cost data to any `is_admin` user regardless of their booleans.

- **Fix:** ship a default-deny base policy (or `canAccess()` returning false unless a capability is present) with the package Resources so the safe default is locked; and/or document that consumers must enable Filament strict authorization mode (missing policy → thrown `LogicException` instead of silent allow). Add a periphery note enumerating every package model that requires a policy mapping.

### SEC M-B. Stock-level reads are not admin-gated — full inventory + low-stock report to any agent-scope caller
**Severity: MED · Confidence: High**

`src/Agent/Tools/GetStockLevel.php:47` and `src/Agent/Tools/ListStockLevels.php:78` have no `isAdmin()` check (contrast `AdjustStock`, `GetRecentProblems`, order tools). Any caller with only the base `agent` scope — i.e. any customer who authorizes a connector — can pull exact `stock_level` for any browsable and a catalog-wide low-stock report (up to 200/page, most-urgent-first). `browseQuery()` limits to storefront-visible items, so not an unpublished-content leak — it's **quantity disclosure** beyond the storefront's in-stock boolean (competitive intelligence).

- **Fix:** decide explicitly. Gate both behind `isAdmin()`, or return `in_stock` boolean for non-admins and full `stock_level` only for admins.

## LOW

### SEC L-A. `CanonicalUrl` falls back to a request-derived URL when `canonical_url` is unset
**Severity: LOW · Confidence: Med**

`src/Agent/Support/CanonicalUrl.php:17` falls back to `url(config('agent.route.path'))`, which derives host from `APP_URL` or the incoming Host header. This value becomes the RFC 8707 `resource` audience and RFC 9728 `WWW-Authenticate`/metadata issuer (`EnforceResourceParameter.php:37`, `AuthenticateAgent.php:240`). If OAuth is enabled but `AGENT_CANONICAL_URL` is unset (and `APP_URL` unpinned), Host-header spoofing influences the advertised audience/issuer → audience confusion. Config comment says "Must be set when OAuth is enabled" but nothing enforces it.
- **Fix:** fail closed — throw at boot when `agent.auth.oauth.enabled` and `canonical_url` is blank.

### SEC L-B. `GetRecentProblems` free-text residual disclosure (self-acknowledged)
**Severity: LOW · Confidence: Med**

`src/Agent/Tools/GetRecentProblems.php:201-206` fingerprints messages (scrubs emails, collapses digit runs) and is admin-gated, but free-text names inside exception messages can still reach the transcript (its own docblock notes this). Admin-gated → low. Effective exposure rises if SEC H-A is exploitable.

## Clean (calibration)
HTTP surface small and enumerated (only Cart API, Agent `/mcp`, Agent OAuth routes register; no Storefront/Payment/Purchasing/Variants controllers or webhook routes ship). Cart IDOR handled (`CartItemController::ensureItemBelongsToCurrentCart:66-73`). No `request()->all()`/mass-assignment in package controllers. All raw SQL interpolates only trusted values (DB-derived ints, hardcoded columns, constant literals). No `unserialize`/`eval`/`exec`/`shell_exec`. No SSRF/outbound fetch on user URLs; DCR validates `redirect_uris` with `FILTER_VALIDATE_URL` and never fetches them. Media uses framework-hashed `store()` paths, server-side `getMimeType()` — no traversal. Bearer + DCR token compares use `hash_equals`. Order tools scope to caller's `customer_id`, `not_found` (not `forbidden`) avoids existence oracle. `Str::random` (CSPRNG) for order numbers. Tool errors map only `InvalidArgumentException` to client-visible messages — no stack traces leaked.

**Still-open prior finding (not re-scored):** H2 guest cart keyed on `session()->getId()` (`ResolveCurrentCart.php:27`) remains unshipped (needs schema migration + cart-token cookie).

# 2. Design / Maintenance Scale

Baseline `docs/audits/2026-05-13/dep-graph-audit.md` (15 domains then). Since: **Support, Purchasing, Variants added; Commerce grew a hard FlowChain dep; both drift items from that audit (Shipping↔Commerce cycle, Inventory→Translation) still unfixed.** Now v0.44.0, 18 providers, 48 migrations, 20 `Has*` contracts, 16 config files.

> **Direction decided (2026-07-02):** the "18 independently extractable domains" goal has been retired in favour of a **modular monolith with one real seam — generic leaves vs. shop core** (see `CLAUDE.md` §"A Modular Monolith With One Real Seam"). This reclassifies several findings below: the Shipping↔Commerce cycle (DES H1) is no longer "drift to fix before a split" — it's accepted coupling *inside* the shop core; the `Shippable` refactor is deferred until a real non-order shipment use case appears. The modular-discipline findings (DES H2 Filament plugin, M1 migrations gate, M2 flowchain config, M3 currency home, M5 architecture test) all **still stand** — they're maintainability wins independent of any split, and M5 becomes the mechanism that keeps the tier boundaries honest.

## HIGH

### DES H1. Commerce is a 10-dependency hub with a live cycle — this is why the "extractable" goal was retired *(direction resolved)*
`src/Commerce/` imports Payment, Inventory, Currency, Location, Support, FlowChain, Pricing, Shipping, Tax, Logging. Shipping↔Commerce cycle persists (`src/Shipping/Models/ShipmentItem.php:11` resolves `Commerce::orderLine()`; `src/Shipping/Actions/CreateShipment.php:10` imports `OrderLine`). Commerce's transitive closure is 12 of 18 domains.
- **Resolution:** this finding drove the reframe. The tiers are now the documented model (CLAUDE.md): **generic leaves** (Currency, Translation, Logging, Location, Media, FlowChain, Support), **middle band** (Pricing, Taxonomy, Payment+Stripe, Tax, Inventory), **shop core = one unit** (Commerce+Shipping+Purchasing), **integration tier** (Storefront, Variants, Agent — never leaves). The cycle is **accepted coupling within the shop core**, not drift. The `Shippable` polymorphism refactor is **deferred** — do it only when a non-order shipment use case appears (warehouse transfer, B2B sample, returns), not to enable a split. ✅ Graph updated in CLAUDE.md/README (Purchasing/Support rows, Commerce→FlowChain, Variants config-read).

### DES H2. The Filament admin layer is the least-designed extension point — per-consumer copy-paste that grows with every domain
Three compounding problems:
- Resources hardcode models, bypassing the registry: `src/Commerce/Filament/Resources/OrderResource.php:35` (`$model = Order::class`), same in all 10. A consumer swapping `commerce.models.order` gets an admin still bound to the package class — "config-driven models" silently doesn't reach the admin layer.
- No Filament Plugin: both consumers hand-list resources in `AdminPanelProvider` (`in-other-worlds/.../AdminPanelProvider.php:26-34`, bianka `:23-31`); the two lists have already diverged.
- Authorization entirely consumer-side: in-other-worlds carries ~9 hand-written policies for *package* models plus `AbstractBooleanPolicy` — a third consumer must re-copy all of it.
- **Direction:** one `InOtherShopsPlugin` (or per-domain plugins) registering resources conditionally; resources resolve `getModel()` through the registry; ship `AbstractBooleanPolicy` + policy base in the package. **(Converges with SEC M-A.)**

### DES H3. Consumer shape-parity files are O(consumers × files) manual diligence
`docs/periphery.md:272-287` ("Part C") lists 6 file shapes (ClaimGuestCart, HandlePaymentSucceeded/Failed, ReserveItems, cartSummary middleware, OrderConfirmation mail) kept parallel across consumers by remembering to check. Works at 2 consumers; fails silently at 3-5.
- **Direction:** the package already owns the right mechanism — FlowChain publish-and-modify. Promote the stable wrappers into package-shipped defaults (a `CheckoutChain`, package `HandlePaymentSucceeded` with consumer hook points) so the default lives in one place and consumers publish-to-customize.

## MEDIUM

- **DES M1. All 48 migrations run unconditionally in every consumer; base provider has no gate hook.** `src/Support/DomainServiceProvider.php:87` loads migrations with no config check (only scheduling got `scheduleWhenEnabled`). A `{domain}.migrations.enabled` hook (default true) is a one-file change buying relief for all 12 regular domains — avoids the per-release gating cost previously judged not worth it. *(Note: memory says "don't gate migrations per-consumer" — a config-default-true gate sidesteps that objection since there's no per-release check.)*
- **DES M2. FlowChain publishing hardcodes an IOW app convention.** `src/FlowChain/FlowChainServiceProvider.php:20` pins `app_path('Project/FlowChains')`; `PublishChainCommand.php:114,132` hardcodes namespace `App\Project\FlowChains`. FlowChain is the only mechanism-bearing domain with **no config file**. Add `config/flowchain.php` with `publish.path`/`publish.namespace`.
- **DES M3. "Default currency" lives in the wrong domain and repeats as a literal.** Keyed `commerce.cart.api.default_currency` with `'EUR'` fallback in 5 sites across two domains (`CartResource.php:21`, `CartItemResource.php:56`, `ResolveCurrentCart.php:20`, `FindOrCreateCartItemStep.php:71`, `VariantsSchema.php:179`). Admin price-editing currency sourced from a *cart API* key is a semantic accident. Add `currency.default` in Currency; one resolver; Commerce key becomes documented alias.
- **DES M4. Test stubs on a pairwise-combination trajectory.** (See scaffolding STUB-1 — same finding.)
- **DES M5. Domain symmetry is conventional, not enforced — newest domains already drifted.** Purchasing and Support are the only domains without a README (checklist step 4, violated by exactly the newest additions); `composer.json:77` branch-alias still `0.15.x-dev` at v0.44.0; Payment on the irregular-provider list despite being textbook-canonical. **Direction:** an architecture test asserting every `src/*` has README + config with `models` key + provider extends base (or explicit allowlist) + contracts match `Has*`. One test file makes symmetry self-enforcing.
- **DES M6. `Currency` enum is a hand-maintained closed set imported by 7 domains.** `src/Currency/Enums/Currency.php:12-30` (3 cases + `symbol()`/`decimals()` match arms). Consumer 3 wanting CHF/SEK/PLN needs a package release touching an enum imported across Commerce/Pricing/Payment/Purchasing/Shipping/Support/Variants. Acceptable while EU-only, but `symbol()`/`decimals()` duplicate `ext-intl` (already required).

## LOW
- **DES L1.** Logging channel map hardcodes sibling-domain names (`src/Logging/config/domain-log.php:28-47`); pricing/shipping channels already absent. Default fallback makes it cosmetic, but it's an inverse dependency + every-new-domain touchpoint.
- **DES L2.** Agent provider's ordering rationale is *wrong* (`src/Agent/AgentServiceProvider.php:24-29`): the real guarantee is the register/boot phase split, not "alphabetical discovery order." Fix the comment before it misleads a future edit.
- **DES L3.** `Has*` naming strain at 20 contracts — `HasCart` on `Variant` means "is cartable" while `HasOrders`/`HasAddresses` mean "owns." Shipping already needed both `HasShipment` and `HasShippability`. Decide a capability-side convention (`Has{X}ability`) before contract #21.
- **DES L4.** `Support` as a domain name will collide if a customer-support domain appears; it's the one `src/*` that isn't a domain. Rename to `Foundation`/`Kernel` only if a split happens.

## Scales WELL (calibration)
`Support\DomainServiceProvider` (12 adopters, declarative hooks, canonical sequence can't drift, `scheduleWhenEnabled` gate, explicit `logSubscriber()` hook surviving `event:cache`) — this is the pattern the Filament layer is missing. FlowChain mechanism scales to more chains with zero per-chain duplication (only flaw is the publish path, M2). Config namespacing clean (one `config/{domain}.php`, no collisions, uniform `models` key). Event/subscriber wiring explicit and uniform (no auto-discovery magic). No Blade views shipped (view-override problem designed out). Factories ship in-package; model-wiring surface is not combinatorial (only the test stubs are).

# 3. DRY / Simplification — Scaffolding Layers

Scope: Filament resources/pages/relation-managers/schemas + `src/Support/Filament`; 18 ServiceProviders + Stripe + `DomainServiceProvider`; `src/*/config`; migrations; factories; test stubs; routes. Overall in unusually good shape — a base provider, base page classes, a money-field home, and a manual-sync trait already exist with documented rationale.

## Filament
- **FIL-1 (MED) — Translatable/media form-lifecycle copy-pasted across 6 pages.** The `mutateFormDataBeforeFill` → `mutateFormDataBeforeSave` (unset) → `afterSave/afterCreate` (saveFormData) dance in: `Taxonomy/.../EditCategory.php:26-45` + `CreateCategory.php` (translations+media), `Taxonomy/.../EditTag.php:15-33` + `CreateTag.php` (translations), `Variants/.../EditOption.php:15-34` + `CreateOption.php` (translations+values). Same 3-hook shape in 6 files. Does **not** use the existing `SyncsManualFormState` trait, so passes raw `$this->data`/`$this->record` — a latent RichEditor/TipTap trap the trait exists to prevent. **Extract** trait `Support\Filament\SavesTranslatableForm` (composes `SyncsManualFormState`, declarative `syncSchemas(): array`) → each page drops to one method and closes the TipTap gap.
- **FIL-2 (MED, drift) — `navigationGroup` scattered string literal with a 'Shop' vs domain-name split.** `'Commerce'` (CustomerGroup/Customer/Order), `'Purchasing'` (Supplier/PurchaseOrder), `'Taxonomy'` (Tag/Category) name the group after the domain; `'Shop'` (Voucher/Option/TaxRate — Pricing/Variants/Tax) collapse. Nothing documents why. **Extract** `Support\Filament\NavigationGroup` enum; decide the Shop-vs-domain policy once.
- **FIL-3 (LOW) — Create pages don't share a base the way List/Edit do.** 10/10 List extend `PackageListRecords`, 10/10 Edit extend `PackageEditRecord`, but all 10 Create extend Filament's `CreateRecord` directly. Asymmetry only (4 Create pages are empty boilerplate). Add trivial `PackageCreateRecord` or leave a one-line note.
- **Clean:** `Support/Filament/MoneyFields` is the single money home, used consistently; the two inline exceptions (`CommerceSchema.php:302-327` live-calc, `VoucherResource.php:51-64` polymorphic money-or-percent) are defensible. No duplicated auth wiring (there is none). `*Schema.php` per domain have no cross-domain copy-paste. `PackageEditRecord`/`PackageListRecords` documented as "default, not a cage."

## Service Providers
- **SP-1 (LOW-MED, drift) — Payment provider re-implements the full base sequence it opted out of.** `Payment/PaymentServiceProvider.php:14-38` does by hand exactly what the base provides (`mergeConfigFrom:16`, `loadMigrationsFrom:24`, `morphMap:26-29`, `publishes:31-33`, `commands:35`, `Event::subscribe:37`) — its only extra is one singleton. Could extend `DomainServiceProvider`, keep the singleton override, drop ~20 lines. The base's "intentional exclusion" reason doesn't hold for Payment specifically.
- **SP-2 (LOW, drift) — `publishesConfig()` inconsistent across the base's children.** True for Inventory/Pricing/Purchasing/Shipping/Tax/Variants; false for Commerce/Location/Media/Taxonomy/Translation despite all having config files. No evident rule. One-line decision.
- **Clean:** the base provider itself (hooks return values rather than act; `scheduleWhenEnabled()` used by exactly the 3 scheduling domains). The 6 irregular providers each carry in-file comments explaining the irregularity. No ordering bugs.

## Migrations *(no `Blueprint::macro` exists anywhere; if adopted, home is a new `Support` provider, not the abstract `DomainServiceProvider`)*
- **MIG-1 (HIGH) — `status` column drift across 5 tables.** Three lengths + inconsistent defaults/index: `orders` string(20)+default('pending')+index; `purchase_orders` string(30)+default('draft')+index; `payments` string(255)+default('pending'), no index; `shipments` string(255)+default(Pending), no index; `stock_reservations` string(255), composite index. **The 20-char cap on `orders.status` is the sharp edge** (`partially_refunded` = 18, one short of overflow). Extract `Blueprint::macro('status', ...)` → length 30 + one index policy.
- **MIG-2 (MED, drift) — hand-rolled morph pairs where 16 siblings use `morphs()`.** `payments` (`:15-16`,+index`:26`) and `payment_profiles` (`:15-16`,+index`:23`) are schema-identical to `morphs('payable')`. `translations` (`:15-16`) is defensibly manual but uncommented.
- **MIG-3 (MED, decision) — cross-domain FK policy inconsistent + undocumented.** `refunds.payment_id` is a soft ref with an explicit independence comment (`create_refunds_table.php:17-21`); `shipment_items.order_line_id` is a hard `constrained()->cascadeOnDelete()` (`create_shipment_items_table.php:16`). Same shape, opposite policy — the cascade means deleting an order line silently deletes shipment history. Given the sync-wipe sensitivities, worth an explicit look.
- **MED — actor-attribution name drift** (`actor_source` in refunds`:34-36` vs `actor_type` in `domain_logs` add-actor migration`:21-23`); **locale length drift** (`translations.locale` string(10) vs `orders.locale` string(8) — `zh-Hant-TW`=10 truncates in orders).
- **Clean:** every PK is `id()`; zero soft-deletes anywhere; every `constrained()` has explicit onDelete; `country_code` string(2) + `sku` consistent; look-like-drift divergences carry in-file comments.

- **Factory-level:** `withAddresses()` duplicated verbatim (`CustomerFactory.php:40-53` == `OrderFactory.php:56-69`) → `CreatesAddressPair` trait; the `Str::slug($name).'-'.Str::lower(Str::random(4))` slug fragment in 4-5 factories → a `Fake::uniqueSlug()` helper; `Currency::EUR` vs `Currency::EUR->value` split (pick one on touch).
- **Bug-smell:** `tests/Stubs/migrations/create_test_localizables_table.php:21-23` declares a redundant index + unique on the same `['locale_group_id','locale']` pair.

# 4. DRY / Simplification — Agent Domain

Scope: 11 tools, `AgentTool` base, Support, Http, DTOs, Events, Listeners, Routes, config.

## HIGH
- **AG-H1. `resolveModelClass()` exists three times.** The "look up `config('storefront.models')[$type]`, throw with available-keys, assert `HasStorefrontPresence`" block: `Agent/Tools/BrowseCatalog.php:87-111` (25-line private), `Agent/Tools/ShowBrowsable.php:80-104` (byte-identical), `Agent/Support/ResolveStockableModel.php:19-47` (same + `HasStock` check; error text drifts: `'Unknown type'` vs `'Unknown browsable type'`). - **AG-M1. Pagination `meta` block repeated in 3 package tools (+4 consumer tools).** Identical 6-line block: `BrowseCatalog.php:128-133`, `ListOrders.php:91-96`, `ListStockLevels.php:95-100` (+4 in-other-worlds tools). **Extract** `protected function paginationMeta(LengthAwarePaginator $p): array` on `AgentTool` — pays off across the ecosystem.

## HIGH

Mechanical, zero behavior change. *(Do L-series dead-code deletion first so the mechanical pass doesn't touch doomed methods.)*
- **DL-H2 — Lock–re-read–sync-back concurrency idiom hand-rolled across 3 actions (5 sync-back sites).** "Open transaction, re-fetch under `lockForUpdate`, guard, push locked attributes back into the stale caller via `setRawAttributes(..., true)`": `Commerce/Order/Actions/ConfirmOrder.php:43-73` (sync-backs :51,:70), `UpdateOrderStatus.php:37-62` (:49,:57), `Payment/Actions/RefundPayment.php:58-77` (:70); `ExpireAbandonedOrders.php:104-119` uses the same frame without sync-back.
